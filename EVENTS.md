# Описание всех событий DLP-агента USB-контроля

Документ описывает полный жизненный цикл событий программного агента DLP-системы:
что происходит на каждом шаге конвейера обработки и зачем это нужно.
Соответствует реализации в `DLP.UsbController.Solution/DLP.UsbController`
(ядро — `Services/UsbDlpAgent.cs`, события UI — `ViewModels/AgentViewModel.cs`).

Общий конвейер:

```
WMI-событие → Идентификация (VID/PID/SN) → Сопоставление томов → Статический анализ
→ Срабатывание политики → Меры принуждения (R/O реестр или карантин)
→ Инцидент NDJSON → Отправка на центральный сервер → Отображение в трее/UI
```

---

## 1. Жизненный цикл агента

### 1.1. Запуск агента — «Агент запущен: мониторинг съёмных носителей активен»
- **Что происходит:** вызов `UsbDlpAgent.Start()`. Поднимается `CancellationTokenSource`,
  запускается `IRemovableDeviceWatcher`: создаются подписки WMI
  (`__InstanceCreationEvent` / `__InstanceDeletionEvent` на `Win32_Volume` с `DriveType=2`)
  и резервный цикл опроса (polling) каждые ~3 сек. Параллельно стартует фоновый цикл
  доставки инцидентов в `NdjsonIncidentLogger`.
- **Зачем:** начать непрерывный мониторинг. Двойной механизм (потоковые события + поллинг)
  нужен потому, что при быстром insert/eject потоковые события WMI могут теряться;
  поллинг гарантирует, что ни одно подключение не пропущено.

### 1.2. Остановка агента — «Агент остановлен»
- **Что происходит:** `StopAsync()` отменяет токен, останавливает и освобождает
  `ManagementEventWatcher`-ы, дожидается завершения цикла опроса, очищает набор
  известных устройств (дедупликацию).
- **Зачем:** корректно высвободить ресурсы WMI и не оставить «висячих» подписок;
  отменённый токен прерывает текущее сканирование (стадия `Failed`, причина
  «Обработка прервана остановкой агента»).

## 2. Обнаружение и идентификация устройства

### 2.1. Событие появления тома — «Обнаружено подключение: E: … ← VID_XXXX&PID_XXXX, SN=…»
- **Что происходит:** WMI сообщает о создании `Win32_Volume` со `DriveType=2`
  (съёмный). Агент получает `RemovableDeviceEventArgs` со списком томов
  `RemovableVolumeInfo`. Для каждого тома создаётся `ScanSessionSummary`
  (стадия `Detected`) и ставится в очередь обработки (через `SemaphoreSlim` —
  одновременная обработка одного подключения, остальные ждут).
- **Зачем:** зафиксировать сам факт подключения и завести «сессию наблюдения»,
  по которой UI (трей/журнал) показывает прогресс. Семафор защищает от параллельного
  скана нескольких томов одного устройства и гонок при массовом подключении.

### 2.2. Сопоставление с аппаратными признаками (VID / PID / серийный номер)
- **Что происходит:** наблюдатель по цепочке assoc-запросов WMI
  `Win32_DiskDrive (InterfaceMatch "USB") → Win32_DiskPartition → Win32_LogicalDisk`
  связывает букву диска с физическим устройством: из `PNPDeviceID` извлекаются
  `VID_xxxx&PID_xxxx` и серийный номер. Формируется `UsbDeviceId` — уникальный
  аппаратный идентификатор.
- **Зачем:** одна и та же флешка может монтироваться под разными буквами, а разные
  копии одной модели имеют одинаковые VID/PID. Только связка VID+PID+SN позволяет
  однозначно опознавать носитель (для белого списка, карантина и отчётов), а
  сопоставление с логическим томом — знать, какой именно буквой пользоваться для скана.

### 2.3. Дедупликация повторных перемонтирований
- **Что происходит:** ключ `"VID_PID;Serial"` добавляется в HashSet известных устройств;
  если том того же устройства появляется снова (перемонтирование, смена буквы,
  сон/пробуждение), событие «подключение» повторно не генерируется.
- **Зачем:** избежать ложных инцидентов и повторных карантинных процедур для
  уже обработанного носителя.

## 3. Проверка политик и белый список

### 3.1. Устройство в белом списке — инцидент `DeviceAllowed` (Severity: Info)
- **Что происходит:** `DlpPolicyConfig.IsWhitelisted(DeviceId, SerialNumber)` совпал —
  агент пропускает устройство без ограничений: ни R/O, ни скан-принуждения.
  В журнал пишется запись `DeviceAllowed` с VID/PID и SN.
- **Зачем:** корпоративные аттестованные носители не должны замедляться и блокироваться;
  при этом факт их подключения всё равно документируется для аудита.

---

## 4. Меры принуждения: режим «только чтение»

### 4.1. Установка R/O — инцидент `EnforcementReadOnly` (Medium/High) + «Том E: переведён в режим „только чтение“ (реестр WriteProtect=1)»
- **Что происходит:** до начала долгого скана `RegistryEnforcementModule.SetReadOnlyAsync`
  пишет `HKLM\SYSTEM\CurrentControlSet\Control\StorageDevicePolicies\WriteProtect = 1`
  (DWORD). Исходное значение запоминается в `DeviceWritePolicyState` для последующего
  восстановления. Если прав администратора нет — операция помечается как dry-run,
  пишется инцидент Severity High («Попытка установки R/O не удалась (требуется elevated)»).
- **Зачем:** закрыть окно риска: пока идёт анализ файлов, пользователь уже мог бы
  скопировать на носитель конфиденциальные данные. Блокировка записи «на всякий
  случай» выполняется немедленно, снимается после изъятия или чистого результата.

### 4.2. Восстановление записи — часть инцидента `DeviceRemoval`
- **Что происходит:** при извлечении тома `RestoreReadWriteAsync` возвращает
  исходное значение реестра (или удаляет параметр, если его не было); фиксируется
  `RestoredAtUtc` в состоянии устройства.
- **Зачем:** не ломать работу других легитимных носителей — политика WriteProtect
  системная; её нужно снимать, когда контроль над конкретным устройством больше не нужен.

## 5. Статический анализ содержимого тома

### 5.1. Начало скана (стадия `Scanning`)
- **Что происходит:** `ContentScanner.ScanVolumeAsync` обходит дерево файлов тома
  (`root = "E:\"`), фильтрует по размеру/расширению, текстовые файлы читает и
  проверяет правилами: регулярные выражения с валидацией (СНИЛС — контрольная сумма,
  ИНН, паспорт РФ, номера банковских карт — алгоритм Луны) и словарями ключевых слов
  (грифы «СЕКРЕТНО», «ДСП», «Коммерческая тайна» и др.). Двоичные/слишком большие
  файлы помечаются `SkipReason` и не прерывают обход.
- **Зачем:** выявить факты хранения конфиденциальной информации (ПДн, грифы,
  финансовые реквизиты) на несанкционированном носителе — это основание для
  применения политики.

### 5.2. Прогресс скана — «Скан E: файлов N, находок M»
- **Что происходит:** `IProgress<ScanProgress>` через `async IAsyncEnumerable` отдаёт
  промежуточные счётчики; они пишутся в `ScanSessionSummary` и транслируются в UI.
- **Зачем:** показать пользователю/администратору живую картину длинной операции и
  отличить «идёт анализ» от «зависло».

### 5.3. Находка содержимого — `ContentFinding`
- **Что происходит:** каждое срабатывание правила превращается в находку: категория
  (`PersonalData` / `Financial` / `ClassifiedMarking` / `Keyword`), относительный путь,
  номер строки, имя правила, уровень серьёзности и **замаскированный** фрагмент
  («4081 **** **** 1234»). Файл с находками становится «скомпрометированным»
  (`FileScanResult.IsCommitted`).
- **Зачем:** категоризация нужна для выбора реакции политики и приоритета инцидента;
  маскировка — чтобы сами логи NDJSON и отчёты не становились каналом утечки ПДн.

### 5.4. Чистый результат — инцидент `ScanClean` (Info)
- **Что происходит:** ни одного скомпрометированного файла; пишется запись
  «конфиденциальная информация не обнаружена», стадия `Completed`.
- **Зачем:** документировать отрицательный результат: для аудита важно не только
  «что нашли», но и «что проверяли и не нашли».

## 6. Срабатывание политики: карантин файлов

### 6.1. Изъятие — инцидент `PolicyViolation` (Severity = max по находкам)
- **Что происходит:** если найдены скомпрометированные файлы и действие политики —
  `QuarantineFiles`, `RegistryEnforcementModule.QuarantineFilesAsync` для каждого файла:
  1) копирует оригинал в защищённый каталог карантина и вычисляет SHA-256 оригинала
     (`QuarantineRecord`);
  2) перезаписывает оригинал на носителе файлом-заглушкой по шаблону `StubTemplate`
     с уведомлением: номер политики, категории найденного, путь в карантине, ID инцидента.
  Затем формируется итоговый `SecurityIncident` со списком всех находок и карантинов.
- **Зачем:**физически изъять контрабанду ПДн/секретных данных с носителя, сохранив
  доказательства (SHA-256 для целостности и юридической значимости) и уведомив
  пользователя на месте — заглушка объясняет, что произошло и куда обращаться.

### 6.2. Регистрация инцидента — «Инцидент xxxxxxxx зарегистрирован и поставлен в очередь отправки»
- **Что происходит:** `NdjsonIncidentLogger.LogAsync` сериализует инцидент в одну
  JSON-строку (NDJSON: каноничная запись на строку, enum-ы как строки, null не пишется)
  и атомарно дописывает в локальный файл журнала под `SemaphoreSlim`; инцидент
  попадает в outbox-очередь доставки со статусом `Queued`.
- **Зачем:** NDJSON — устойчивый к дописыванию потоковый формат: не требует
  переписывания файла, читается построчно, импортируется прямо в SIEM/ELK. Локальный
  журнал — доказательная база, переживающая недоступность центра.

### 6.3. Отправка на центральный сервер (имитация) — статус `Delivered` / `Failed`
- **Что происходит:** фоновый `DeliveryLoopAsync` выбирает инциденты из очереди и
  «отправляет» их на смоделированный сервер DLP (`SimulatedDlpServer`): статус
  меняется на `Delivered` с временной меткой либо `Failed` с текстом ошибки и
  последующим ретраем. При рестарте агента неотправленные записи восстанавливаются
  из журнала.
- **Зачем:** в продуктиве здесь HTTPS POST с сертификатом; в демо транспорт
  имитируется, но механика важная — гарантированная доставка (at-least-once)
  и переживание сетевых разрывов — отрабатывается уже сейчас.

## 7. Извлечение устройства

### 7.1. Событие удаления — инцидент `DeviceRemoval` (Info)
- **Что происходит:** WMI `__InstanceDeletionEvent` по тому же фильтру; агент вызывает
  восстановление R/W (см. 4.2), пишет «Том E: отключён. Права записи восстановлены:
  да/нет/не требовалось», удаляет сессию из активного набора и снимает ключ из
  дедупликации (следующее подключение будет обработано заново).
- **Зачем:** завершить жизненный цикл контроля: состояние реестра не должно «течь»,
  а UI — показывать фантомные активные тома.

---

## 8. Ошибки и нештатные ситуации

### 8.1. Сбой обработки — инцидент `AgentError` (High) + стадия `Failed`
- **Что происходит:** любое необработанное исключение в конвейере перехватывается,
  текст ошибки кладётся в `ScanSessionSummary.LastError`, пишется инцидент, семафор
  всё равно освобождается (`finally`).
- **Зачем:** один сбой (битый том, отказ доступа) не должен убивать агент или
  блокировать очередь навсегда; ошибка видна в журнале и UI.

### 8.2. Отсутствие прав администратора — dry-run вместо блокировки
- **Что происходит:** при неудачной модификации реестра агент не падает, а переходит в
  щадящий режим (dry-run) и регистрирует High-инцидент.
- **Зачем:** честная деградация: администратор центра видит, что станция формально
  под контролем, но принуждение не активно, и может принять меры.

## 9. Отображение в интерфейсе (system tray + GUI)

### 9.1. Поток активности в UI
- **Что происходит:** события `ActivityLogged` (текст с таймстампом) и
  `SessionUpdated` (сводка `ScanSessionSummary`: стадия, счётчики файлов, находки по
  категориям, применённое действие) подписаны в `AgentViewModel`; маршаллинг в UI-поток
  через `InvokeRequired/BeginInvoke`.
- **Зачем:** агент работает в фоновых потоках, а WinForms-контролы требуют обращения
  из UI-потока; троттлинг обновлений предотвращает «лавину» перерисовок при частых
  событиях прогресса.

### 9.2. Иконка в трее и журнал событий
- **Что происходит:** `AgentForm` с `NotifyIcon`: цвет/tooltip отражают состояние
  (мониторинг активен / идёт скан / есть инциденты). Контекстное меню и окно
  `IncidentLogForm` показывают детализированный журнал (последние инциденты,
  категории находок, статусы доставки).
- **Зачем:** пользователь не должен лезть в NDJSON-файл: состояние контроля видно
  всегда, а по двойному клику доступна полная детализация инцидентов для разбора.

## 10. Сводная таблица типов инцидентов (EventType в NDJSON)

| EventType | Severity | Когда возникает | Действие принуждения |
|---|---|---|---|
| `DeviceAllowed` | Info | Устройство из белого списка подключено | None |
| `EnforcementReadOnly` | Medium / High | Установлен (или не удалось установить) WriteProtect=1 | SetReadOnly |
| `ScanClean` | Info | Скан завершён, находок нет | None |
| `PolicyViolation` | Max по находкам | Обнаружена конфиденциальная информация | QuarantineFiles / SetReadOnly |
| `DeviceRemoval` | Info | Том извлечён, права восстановлены | RestoreReadWrite / None |
| `AgentError` | High | Неизвестный сбой конвейера | None |

Каждая запись содержит: ID (GUID), UTC-временную метку, VID/PID, SN, модель и
производителя, буквы томов, hostname/username станции, описание, применённое
действие, количество и список находок (маскированных), карантиновые записи
(SHA-256, пути) и статус доставки (`Queued/Delivered/Failed`).
